# 数据即护城河:给十年后的数据设计格式

- @author 十四叔
- @date 2026/08/01
- 状态: 草稿(待校订)

---

我的十年战略里有一条"数据复利":用户在应用里沉淀专注记录,换工具等于丢历史,于是续费动机成立。护城河长在用户侧的数据上。

既然是护城河,**数据完整性就是产品第一性**。所以我给番茄钟做会话记录数据层时,想的不是"这个版本怎么存",而是"十年后这堆数据怎么活着"。

## 第一原则:格式要能活十年

一份要活十年的数据格式,第一件事是**版本化**。我在历史文件的顶层放了 `format_version`,每条记录的所有字段都加了 `serde(default)`。

这意味着什么?明年我想给记录加一个字段(比如"这轮专注是否被打断"),老文件读进来,缺的字段自动填默认值——**旧数据不用迁移,新字段平滑生效。** 反过来,一个十年前的老版本程序读到今天的新文件,它认识的字段都还在,不崩。

这是版本化的"读"一侧。真正难的是"写"一侧。

## 第二原则:未来的数据,旧版本不许覆盖

降级是真实场景:用户用新版用了一年,某天为了某个原因装回旧版。旧版读到新格式文件——如果只是 `format_version` 高了,我让它拒读;但更阴险的情况是,新版改了字段**类型**,比如把时间戳从数字改成了字符串。这时候旧版的 JSON 解析直接失败,返回一个空历史。

然后,用户在旧版里完成了一个专注。程序把"空历史 + 这一条"写盘——**新版本一年的数据,被一条记录覆盖了。** 这是数据护城河上最不该发生的事。

所以我的加载逻辑是:**文件不存在 → 空历史(可写);文件存在但读不出或解析不出 → 空历史,但标记"拒写"。** 之后所有保存路径检查这个标记,一旦置位,一律拒绝写入,宁可让新数据只在内存里活一个会话,也绝不覆盖磁盘上可能更新的数据。

我把"拒读"和"拒写"绑定在一起。读不出来的时候,你根本不知道磁盘上是什么,所以唯一安全的行为就是别碰它。

## 第三原则:能用一个常量,就别用一个累加器

记录一条专注会话,最自然的设计是"会话开始时打时间戳,运行时逐帧累加专注秒数,完成时写盘"。我一开始就是这么写的,然后发现逐帧累加是个坑。

第一坑:60fps 下,每帧 16 毫秒,`as_secs()` 截断后是 0,累计永远是 0——改毫秒累加才修好。

第二坑(更隐蔽):如果程序被冻结了半小时——比如合上笔记本、主线程被拖住——醒来时单帧跨过了好几个阶段。这时累加器会把整个冻结期摊进"专注时长":我的评审用一个探针复现,两条记录各声称专注 3900 秒,合计 7800 秒,而实际专注只有 3000 秒。**累加器在极端时序下会污染数据本身。**

然后我停下来想:真的需要累加吗?自然完成一个专注,意味着计时器从满量一直跑到 0——**暂停会冻结剩余时间,所以实际专注时长恒等于计划时长。** 这是一个常数,不是一个累加值。

于是我把整个会话追踪机制删掉了。`focused_secs = planned_secs`,开始时刻由"完成时刻减去计划时长"推得。一个常数替换掉一个累加器,同时消灭了三个 bug:冻结期污染、恢复中途时间戳不真实、完成时没追踪到会话就不记录。

这是我喜欢的那种简化:**更少的机制,更少的错误面。**

## 结尾

数据是护城河,所以这套格式的每一行都在回答同一个问题:**十年后,一个没有文档、没有我解释的人,能不能无损地读懂这些数据?**

版本化字段让它能活,拒写保护让它不被杀,常数替代累加器让它不被污染。格式本身,就是护城河的一块砖。
