# Spec: round10 选型指南（2026-10-20）

> 状态：**待用户批准**。批准后才进 plan；本 spec 不写产品代码、不开枪、不动当前队列。
> 上游意图：`danqing/docs/intent/selection-round10-intent-2026-10-20.md`（用户 explicit yes，2026-10-20）。
> 本 spec 是流程规格，不是产品规格；产出是复审台账与候选卷，不是可执行软件。

## 1. Objective

把意图文档的三条判据写成**可执行闸门**，并先用它复审既有弹药。产出二选一：

- **有候选**：过三道闸的候选卷 + 调研三闸（裁决段 / 红队 / 粗算），交用户裁决；
- **零候选**：逐条死因台账 + 是否开新域扫描的请示（不得自动开）。

用户：十四叔。判定标准是「值不值得再投入一段生命」，不是「有没有道理」。

## 2. 适用范围与非适用项

本 spec 无代码，因此标准六区中的 Commands / Project Structure / Code Style / Testing Strategy **不适用**，以下列替代：

| 标准区 | 本 spec 的替代 |
|--------|----------------|
| Commands | 作业规则（第 4 节：顺序、时间盒、证据格式） |
| Project Structure | 产出结构（第 5 节：文件位置与台账格式） |

## 3. 闸门序列（核心）

**顺序固定，命中即停。** 前一闸不过，不进入后一闸，不浪费证据收集。

### Gate 0 · 去重

- 命中累计死池（round4–9 拒清单 + 已埋产品：clipboard 商业化 / xirang / disk / tile）→ 直接跳过并记录命中项。
- 命中已扫域且无新扰动 → 跳过并记录。
- 输出：`命中 / 未命中` + 命中依据。

### Gate 1 · agent 吃不掉（第一闸，不可跳过）

**核心问句：**

> 目标用户手上已经有 Claude Code / 豆包 / WorkBuddy，他为什么还要买这个？

**三个可接受答案，至少一条成立且要有用户侧证据：**

- **A 想不到**：不知道这个解法存在，也不会主动去问 agent。
- **B 做不好**：做得出，但描述、审美、调试、维护的成本 > 售价。
- **C 不敢信**：自己造的不敢用于真实数据、长期使用或承担责任。

**死刑句（命中任一即死）：**

- 核心价值 = **一次转换 / 一次生成 / 一次搬运**；
- 成品是**一次性输出**，不是持续使用的工具；
- 用户**一个提示词就能拿到同样结果**，且没有后续维护成本。

**证据要求：** 一句判定 + 理由 + 至少一条用户侧证据（原话 / 行为 / 竞品形态 / 定价）。

**校准样例（用于自检闸门是否过松或过紧）：**

| 样例 | Gate 1 判定 | 理由 |
|------|-------------|------|
| luoban | 死 | 核心是 MD → inline-CSS 转换，一个提示词可得 |
| dropshelf | 活 | OS 层拖拽，agent 替不了；但需继续过 Gate 2 |
| clipboard | 活 | 常驻 + OS 集成 + 每天使用 |
| loglens | 活 | 持续使用的大文件查看器，不是一次性输出；死于 Gate 3 |

若校准样例判不出来，说明闸门定义有问题，先修闸门，不审候选。

### Gate 2 · 需求真实

- ≥3 个独立来源，落在近两年，**带日期**；
- 行为证据优先于言词抱怨；**付费行为证据单列**；
- 看帖子 / issue 的**创建日期分布**判断需求衰减，不看总票数；
- 必须写死**失效标志**：出现什么证据 = 这条需求判断错了。

输出：`活 / 死` + 证据清单 + 失效标志。

### Gate 3 · 陌生人掏钱

- **二值判定**：是否存在陌生人为同类价值付费的实证。
- 可接受：竞品真实销量 / 续费 / 评分量、用户为邻近品掏钱、同类买断产品的实际成交证据。
- **不接受**：star、下载量、装机量、「有人问过」、「我觉得会买」。
- 输出：`有 / 无` + 证据（URL + 日期）。

### 过闸后 · 调研三闸

每个活着的候选逐项执行，缺一不进裁决：

1. **裁决段**：继续 / 放弃 / 转向 + 依据；
2. **红队**（doubt-driven）：逐条攻击假设；
3. **一页粗算**：渠道可见流量 × 转化 × 单价 vs 预计工时。

## 4. 作业规则

- **复审顺序**：C 存量待判（dropshelf / luoban）→ A round9 幸存者 → B 0→1 六案。先近后远，先用已有上下文。
- **逐条串行**：一条走完 Gate 1→2→3 再下一条，不并行堆证据。
- **证据格式**：`结论 + URL + 日期`，一句话死因；不贴整屏、不复述原文。
- **时间盒**：复审默认 1 个工作会话内完成；超时则记录已完成条目并请示，不硬拖。
- **复审对象清单**：
  - **C 存量待判**：dropshelf、luoban（均已建成、未验收）；
  - **A round9 幸存者**：物格转向、5 采访员、徒弟（已归档）、A2 log 家族、A1 体裁、A3 iPhone、A4 多显示器、Hazel；
  - **B 0→1 六案**：`intent-0to1-innovation-2026-10-17.md` 候选池 1–6（按该文档编号引用）；
  - **不复审**：log v1.x（在制已发布，组合纪律保护）。
- **重复条目**：同一方向在多处出现（如 A1 体裁 = luoban、物格在两卷均有）只审一次，台账注明所有来源。

## 6. Boundaries

**Always（必须做）**

- 每条结论带证据 URL 与日期；
- 先查死池再评估；
- 按 Gate 1 → 2 → 3 顺序，命中即停；
- 零候选时如实记录，不自动放闸；
- 复审只出建议，存量产品的「继续 / 埋掉」由用户裁决。

**Ask first（先问）**

- 开新域扫描；
- 复活任何已埋产品；
- 放宽或调整任一闸门；
- 修改本 spec 或意图文档的判据。

**Never（禁止）**

- 写产品代码、建产品仓；
- 用 star / 下载 / 装机当需求或付费证据；
- 跳过 Gate 1；
- 把「够大」排在「agent 吃不掉」前面；
- 未获指示 commit / push。

## 7. Success Criteria

- [ ] 复审台账覆盖 C + A + B 全部条目，无遗漏；
- [ ] 每条至少一行 `pass / fail` + 证据 URL + 日期；
- [ ] 所有存活候选按 Gate 1 → 2 → 3 全过，且带调研三闸与裁决段；
- [ ] 若零候选：逐条死因完整，且含开新域扫描的请示（不自动执行）；
- [ ] 用户对最终结果有明确裁决（继续 / 放弃 / 开新域）；
- [ ] 全程零产品代码、零 git 提交。

## 8. Open Questions

1. **判据 ③ 丢弃后的质量兜底**：默认完全交给 `PRODUCT-DEV-GUIDE.md` 发布前闸，选型阶段不再设质量条。默认成立，除非你另有指示。
2. **存量两件的处置权**：复审只出「继续 / 埋掉」建议，最终由你裁决；不自动埋、不自动重启。
3. **「徒弟」是否复审**：它已归档，归档理由是付费证据全在企业侧，不是 agent 可替代性——默认纳入复审，若你判定不必回头可直接划掉。
4. **时间盒**：默认 1 个工作会话；若你要更短或更长，在 plan 阶段改。
